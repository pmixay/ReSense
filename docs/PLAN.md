зрения, разработчик робототехники (ROS 2), специалист по работе с данными, разработчик ПО
(C++/Python). На четверых они распределены так (капитан — лид, второй участник — фронтенд):

Разработка ПО (C++/Python) как отдельная роль не выделяется: пайплайн на Python делают все
четверо, каждый в своей зоне; если понадобится C++ (производительность на стенде), это берёт P3.

Правило: каждый PR — через ревью одного другого участника; ветка `main` всегда собирается
в Docker и проходит `pytest`.

## Бэклог по направлениям (приоритет ↓)

### Алгоритм (P3)
1. Кривизна/рыскание оси пути по стенам: устойчивость на платформах, стрелках, гермозатворах
   (сейчас берётся ближняя граница; добавить временную фильтрацию и проверку по рельсам).
2. Полигон габарита по ГОСТ 23961-80 (габарит подвижного состава метро + запас); «платформенная»
   выемка; верх коридора против подвесных кабелей/светильников.
3. Ego-motion: оценка скорости по бэгу (сдвиг пола/стен между кадрами, ICP по ближней зоне) →
   трекер предсказывает положение, накопление кадров в мировой системе (5–10 кадров) для 150–300 м.
4. Модель «нормального тоннеля»: ожидаемая дальность на луч (range-image) → аномалии внутри габарита.
5. Подавление FP: статичные структуры на границе габарита (колонны, край платформы, стрелочные
   приводы) — фильтры по форме + «карта известных структур» вдоль пути (если есть повторные проезды).
6. Замер задержки/FPS на стенде (i7-9700E), профилирование, при необходимости Numba/C++.

### Данные и оценка (P4)
1. `resense inject`: набор объектов (человек, ящик 0.2/0.5/1 м, доска, тележка), дальности
   10–250 м, отрицательные примеры вне габарита; калибровка dropout/интенсивности по реальным
   препятствиям из расширенного датасета.
2. Разметчик реальных препятствий (вместе с P2), формат `gt.json` совместим с `resense eval`.
3. Метрики: recall по бинам дальности, дальность первого обнаружения, FP/км и FP/час на пустых
   бэгах (по причинам), задержка p95, FPS.
4. Тесты на синтетике для каждого модуля, CI (GitHub Actions: `pytest`, сборка Docker).
5. Аугментации фона (dropout, шум, повороты крепления) для проверки устойчивости.

### Интеграция (P1)
1. Docker-образ: сборка «с нуля» без ручных шагов; `docker compose` профили (detector / viz / player).
2. ROS 2: параметры ноды, QoS, сообщения (`vision_msgs/Detection3DArray`, флаг, дистанция,
   маркеры); при необходимости свой `resense_msgs/ObstacleArray`.
3. Скрипт демонстрации: один командный файл — контейнер + bag play + RViz/Foxglove.
4. Сбор документации по требованиям ТЗ (README, архитектура, алгоритм, эксперименты, видео).
5. Чек-лист сдачи (ниже) и связь с организаторами.

### Визуализация и презентация (P2)
1. RViz: облако + коридор + боксы + текст «PATH CLEAR / OBSTACLE 87 m».
2. Foxglove-layout (через `foxglove_bridge`) — удобно для удалённой демонстрации.
3. Веб-дашборд `web/` (Three.js + rosbridge/websocket): вид сверху и 3D, шкала дальности,
   журнал тревог, FPS/задержка.
4. Видео 1–2 мин: тоннель → облако → алгоритм → «препятствие за X м».
5. Презентация по шаблону: слайды 7–11 обязательны и без изменений дизайна (см. `docs/PRESENTATION.md`).

## Риски
- Расширенный датасет придёт поздно → синтетика как основной источник позитивов; держать
  разметчик и `eval` наготове.
- Кривые и станции дают FP → без надёжной оси пути дальность > 100 м не имеет смысла; это
  главный технический риск, работать первым.
- Производительность Python при 300k точек/кадр — сейчас 40–80 мс/кадр на 4 ядрах, запас есть;
  накопление кадров может удвоить нагрузку.
- Стенд организаторов без GPU-зависимостей: не тащить CUDA в обязательные зависимости.
