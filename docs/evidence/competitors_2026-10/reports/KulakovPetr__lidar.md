# KulakovPetr/lidar

## Verdict
Classical single-frame geometry, no learning, no tracking in the shipped profile. Early prototype (team "Лидарный Дозор"). Package: `repository/src/obstacle_detector/obstacle_detector/`, 15k LOC, of which about half is ROS/queue/viewer/eval plumbing. It is far less mature than ReSense. The only metric claimed is "98.7 m" on one organizer synthetic object ("E01 face", cloud_with_fake_obj). It is a single in-sample number, measured on a "short run", and the deck itself says the screenshot shows 90.1 m. There is no FPR, no empty-ride result, no ablation and no result file in the repo. The README and deck openly say path, small objects and false alarms are unmeasured. Trust: low, but the authors are honest about it.

## Pipeline
1. `repeat_groups.py:group_exact_xyz`: drop (0,0,0)/non-finite points and collapse exact-duplicate float32 XYZ (dual return) into one "vote".
2. Fixed sensor prior s=-Y, l=X, h=Z, mount unconfirmed (`corridor.yaml: mount.confirmed=false`). `local_ground.py:estimate_ground` uses height histograms (5 cm bins) in 2 m s-segments over s=5..30 m. The lowest wide mode linked along s is "ground". It then fits a per-segment line h(l), plus a summary plane by RANSAC.
3. `straight_corridor.py:geometric_membership` is the configured straight box: |l|<=1.05, h from the ASSUMED rail head at -1.075 m (lidar height from the organizer webinar, zero angles) up to +3.0 m, s=1..120 m. No rail fit is used to build the corridor. `pair_geometry.py` and `axis_compatibility.py` only decide whether a strong, consistent rail pair contradicts "straight" (then the frame is marked inapplicable).
4. `detector.py:detect`: ground points whose dh is below the fit residual (or below half of 10 cm) are removed. If the p95 residual >= 5 cm they go into an "ambiguous layer" and are NOT deleted. Remaining points go through graph clustering with a 0.15 m link radius (0.23 m beyond 70 m). Optional `local_protrusions` then looks for local-plane protrusions inside the ambiguous layer.
5. `intrusion_rule.py:decide`: one frame, no confirmation. Evidence is "volume" (>=8 unique points, height >= 0.10 m, horizontal extent >= 0.30 m), "vertical_face", "thin_fragment" (>=0.8 m, >=10 points, >=1 m above the floor) or "low_protrusion". Output is the minimum lidar range of the candidate points. `tracking.py` (2-of-3 frames, KISS-ICP pose) is disabled (`kiss_icp:false`, needs a pose and `registration_reliable`).
6. Runtime: ROS node, 2 worker processes, queue_policy=keep_latest, per-frame budget 30 s. 3.12 results/s on a 10 Hz bag (1509 results in 483 s, deck slide 13), so it is NOT real time.

Honest summary: the only item that is both missing in ReSense and not already measured by us is #1 (the holdout-based per-patch threshold), and it is a variant of the local-support experiment that we found not useful. There is no technique here aimed at platform/switch/column false STOPs.

## Things done worse than ReSense / red flags
- The corridor is a fixed box in sensor axes at an ASSUMED rail-head height of 1.075 m below the sensor, with no calibration. Pitch/roll are not estimated, and a 0.5 deg pitch is about 0.9 m of height error at 100 m. Ground is estimated only for s=5..30 m: `height_above_local` returns NaN outside it, so `near_surface` is False. Beyond 30 m there is no floor filter at all, only the assumed rail-head plane. The "98.7 m" result is therefore not comparable with ReSense range numbers.
- No tracking, no confirmation, no hysteresis in the shipped profile (single frame decides), and no FPR measurement. One real-data fact: the deck lists "false alarm labelling" as an open question.
- Not real time: 483 s for 151 s of data (3.12 results/s), median latency 115 ms but the frame budget is 30 s. Per-point Python graph clustering, so a native C component is needed.
- Eval tooling has oracle gates hard-coded to specific synthetic objects (`corridor_probe.py:gate_e01`, `gate_e03`: fixed s/l/h boxes) and a hand-built `locate_face`. This is in-sample by construction.
- Large share of the code is documentation-style hedging (`*_is_not_*` flags) and plumbing, with little algorithmic content. README wording is cautious, with no overclaiming, and the claims match the code (it is consistent that the 98.7 m figure is "visible surface of E01", not an FPR-tested range).

## Eval/data tooling worth borrowing
- Manual-mark visibility table by surface and range band (`manual_marks.py`) as an honest sensor-limit estimate. Same discipline: "no mark" is not "not visible" and algorithm proposals are refused as labels.
- Azimuth x elevation range image with all point indices kept per bin (`angular_projection.py:project_xyz`) for click-labelling. We already rejected range-image anomaly detection, but it is useful as a labelling aid only.
- `check_result.py`: bit-for-bit regression of two offline result journals (membership of candidates, ranges within 1e-5 m, config/algorithm version hashes). A cheap way to guard our C++ vs Python kernels and refactors.
- Nothing else (no datasets, no labels, no FPR scripts).
