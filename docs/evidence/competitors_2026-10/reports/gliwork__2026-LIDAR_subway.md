# gliwork/2026-LIDAR_subway

~9.3k LOC, but only `shadow/docker/src/*.py` (~6k LOC, 16 scripts) touches LiDAR bags. The repo root (`laser_radar_final.py`, `laser_sensor.py`, `measure.py`, `calibration*`) is a different product: a 3-laser-fan + USB-camera triangulation sensor with range 2-13 m, no relation to the Hesai bags. Single commit, no result files, no logs, no metrics for the LiDAR part.

## Verdict
Exploratory classical geometry / visualisation scripts, low maturity: no online detector with GO/STOP output, no evaluation, no FPR, no held-out anything. The LiDAR README only documents a Docker wrapper for video/PNG output. Nothing here is a trustworthy metric; the only "result" claims are in docstrings (e.g. synthetic-box catalogue) and are not backed by files. Little to borrow.

## Pipeline
LiDAR part (several unrelated tools, offline, run per bag):
1. `slice_detect.py` (closest to a detector): per frame find rails (`detect_rails`: topmost flat z sub-band in +-band of candidate centre, mirror from gauge 1.52 m when one rail seen), fixed rectangle 3.0 m wide x 2.1 m above rail head, 2 m range chunks to 60 m, grid union-find clusters (eps 0.25, >= 3 pts, size >= 0.1 m); rail level / centre median over last 6 frames; offline consolidation "STABLE" if seen in >= max(3, 30 %) of all frames.
2. `rosbag_shadow(_stream).py`: "decision plane" at D0: every ray lands at (u,v)=(lat*D0/f, ver*D0/f), state open / lit (nearest return beyond plane) / occluded (in front); reference = per-pixel fraction lit over a sliding window (or whole bag); SHADOW = lit in reference, not now; OBJECT = lit now, not in reference. Output video/PNG/masks only.
3. `lidar_slices.py` + `shadow_detect.py`: angular screens (a=y/f, b=z/f) at many planes D; a box makes cell counts drop in a sharp step when the plane passes its back face, walls/floor decay as a ramp; groups drop cells into boxes, cross-checks drop position vs linear growth of apparent width.
4. `obstacle_map.py`: whole-bag (range 2 m x lateral 0.1 m) occupancy map, excess over local median along range, Poisson-significance window test per organizer box class (2x2, 0.3x0.3, 2x0.2, 0.05 hanging).
5. `tunnel_model.py`, `tunnel_section.py`, `vsection.py`, `lidar_proj.py`, `far_points.py`, `bag2video.py`, `db3_to_las.py`: walls/floor/ceiling vs range, cross-section sheets, far-return classification, converters.

## Things done worse than ReSense / red flags
- Fixed straight 3.0 x 2.1 m rectangle centred between rails, no curvature, no axis-range limit, no infrastructure rejection, dmax 60 m, offline "STABLE >= 30 % of frames" as the decision; would flag every platform/switch/column.
- Several scripts (`vsection.py`, `lidar_proj.py`, `tunnel_section.py`, `obstacle_map.py`) read the PointCloud2 by a raw `[200:]` byte offset and conclude "the cloud is 2.5-D, the z slot is a 0..255 attribute, no height" (docstrings). Our DATASET.md documents real float32 x,y,z + intensity; the claim looks like a parsing error (other scripts use proper CDR deserialisation). Anything derived from those scripts (top-down maps, section sheets) is unreliable.
- Root README claims (wall RMS 0.22 m, 0 spurious objects) are on 28 calibration photos of a flat board in a room, i.e. the calibration set itself, for the unrelated laser-camera sensor.
- Docstring claims about the organizer-object catalogue ("2x2 centre, 0.3x0.3 on rail / gauge edge / outside, 2x0.2 on rail, 0.05 m hanging from ceiling") are not backed by any shipped output; we already have per-object labels (`labels/cloud_with_fake_obj.json`).
- Docs are machine-spaced text; Docker image only wraps video generation.

## Eval/data tooling worth borrowing
