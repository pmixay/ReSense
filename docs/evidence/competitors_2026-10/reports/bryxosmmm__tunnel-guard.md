# bryxosmmm/tunnel-guard

## Verdict
Classical geometry (KISS-ICP ego-pose + rail/bed fit + range-adaptive density clustering + Kalman/Hungarian tracking), no learning. Mature as engineering and documentation (one squashed commit, 29.09, about 15k LOC incl. many audit/report scripts, C++ kernels, ROS 2, review viewer), but as a detector it is clearly weaker than ReSense: no FPR/km figure, no range curve, no recall beyond one hand-labelled person. Its own docs report that the corridor is certified only to a median 62 m (p10/p90 56/67.5 m), that far objects are only "unresolved", and that the labelled person is `adjacent` (not `intersecting`) on all 36 labelled frames. Headline "99/105 matched frames" is box-IoU localisation of one person (in-sample, translation-propagated labels), not recall. Treat metrics as weak evidence; the repo is useful mainly for one structural idea and a few evaluation tricks.

## Pipeline
1. io.py/detector.py: decode PointCloud2 (keeps intensity/ring/time but does NOT use them in decisions), range crop 1-220 m, 8 m lateral window, voxel 5 cm.
2. Motion: KISS-ICP (default) or opt-in longitudinal side-wall profile correlation (profile_motion.py, copied from EhimenNathan/tunnelguard-lct2026 `adapt.py`; ReSense egomotion.py already does the same idea).
3. geometry.py:TrackGeometry: RANSAC bed plane (sensor frame, 2-25 m, 180 trials) -> piecewise ground profile -> rail pair by histogram peaks refined by joint lstsq (centre, gauge, slope) in sliding windows -> `path(x)` with uncertainty 0.06+0.008d+0.0003d^2 plus continuation covariance beyond the last anchor; GOST-23961 M contour (1.44 m half-width), not 2.1 x 3.0.
4. background.py: Open3D RANSAC longitudinal wall/ceiling planes with per-strip support and normal checks; background is removed only from non-protected "context" points.
5. geometry.py:structural_mask: per-return tunnel cross-section test (see candidate 1).
6. segmentation.py: mutual-radius density graph (radius grows with range, core threshold scales (20 m/r)^2), separation of bodies standing on the running surface.
7. detector.py:_associate: constant-velocity Kalman in world frame, Mahalanobis + log-extent gate, `linear_sum_assignment`, hits/evidence accumulation in object-centred frame within 0.5 s.
8. Output: five states (obstacle / unresolved_obstacle / candidate / no_obstacle_observed / unknown), presence vs intersection confirmation kept separate, per-object distance = nearest point of the contour-certified support.

## Things done worse than ReSense / red flags
- Detector never reaches a usable decision beyond about 62 m: certified corridor p50 62.5 m; 3650 observations on 96-197 m are `unmeasured_corridor`; `unresolved_obstacle` on 59/60 frames of an empty tunnel (docs/FAR_FIELD_ALARM_DECISION.md). They consciously leave the empty-tunnel alarm load unsolved ("six approaches failed").
- Pre-fix full ride (11,271 frames, 13 km class): 505 confirmed-intersection episodes, 10,189 `unresolved` frames (docs/EXTENDED_FULL_RUN.md). The post-fix numbers exist only on a 1274-frame sample (obstacle 7, unresolved 32, candidate 5); no episodes/km on the full ride after the fix, so nothing comparable to our 2.3 STOP/km. On the other five real bags still 84 hazard frames of 2287 (3.7 %).
- Never detects or labels the organizers' object on the rail (only the person); 0.3 m box inserted at 60 m has 0-2 unique returns and no confirmation in their own ray-insertion panel; 100 m insertions on platform bag got zero returns.
- Not real time: 0.13 s median / 0.2 s p95 (native, M3) on the shipped run, 0.9-1.6 s per frame in older Python runs; ICP in a translation-invariant tunnel (their own O2 states the longitudinal drift problem).
- Docs and README honest about limits but contain one retracted claim (a corridor-crop feature silently disabled for a day while the README advertised it) and a retracted attribution (GOST vs 2.1x3 m frame counts); single squashed commit hides history. `lct_astra_review_and_build_prompt.md` (48 KB prompt file) and AGENTS.md are agent instructions; ignored.
- Intensity/ring/time decoded and stored but unused (O3), no deskew; GOST M contour (1.44 m half-width) differs from the organizers' 2.1 x 3.0 m and from ours.

## Eval/data tooling worth borrowing
- Annotation schema flag `exhaustive: false` (annotations/*.json): unmatched predictions in non-exhaustive frames are unscored, plus an explicit "object not there" marker frame; avoids counting FPs on partly labelled frames.
- Semi-automatic labelling: hand-anchor a box at 3 frames and propagate by translation-only nearest-neighbour registration of the box's own returns (provenance in annotations/doubleT-obstacle-person-crossing.json, tunnel_guard/annotate.py, sustech_import.py with vendored SUSTechPOINTS); cheap way to label tracks on new recordings.
- Independent cross-check of our labels: their person label says the person is outside the contour frames 0-6, inside 7-68, outside from 70; our labels/doubleT_obstacle.json person_crossing has in_gauge False 0-7, True 8-68, False from 69. Two independent labellings agree to 1 frame, supporting our in_gauge ground truth.
- Stage-attrition tracing of labelled/inserted points through each pipeline stage with `ran` vs `not_run` (tunnel_guard/trace_analysis.py, injection_experiment.py counts slots vs unique positions after grouping same-timestamp same-direction returns): we already have occlusion-correct insertion (resense/synthetic.py) and oracle protocols, so only the unique-position vs slot accounting is new.
- HMM-MOS review (docs/HMM_MOS_REVIEW.md, results/hmm-mos-probe-20260918.json): measured that moving-object segmentation labels 0 returns of a static object at 15-100 m and floods at metro speed; confirms we need not try MOS. Also records that each measurement is duplicated in the bag (decoded count 0.51x), which ReSense already handles.
