# ikonushok/lidar-metro-obstacle-detection

## Verdict
Hybrid: classical geometry (paired rail ridges -> tangent-extended envelope -> connected components) plus a hand-written C++ 17-tree "forest lite" and two hard-coded shape rules (C++ core ~2.6k LOC; rest is player/ROS/docs; the repo also carries LLM-agent prompt files `AGENTS.md`/`agents/`, which were ignored). The authors' own audit (`docs/GENERALIZATION_ASSESSMENT.md`, `docs/reports/generalization/`) says it is overfit; the code confirms it. Claimed 51/52 on doubleT_obstacle, 47 FP frames on the 20-min ride, 6/6 on fake objects: not trustworthy (positives from one event, all negatives used as hard negatives, synthetic scored by "any alarm in a frame window", no spatial match).

## Pipeline
1. `src/cpp/auto_rails_core.cpp:DetectAutoRails`: per 2 m station, per 4 cm lateral cell head height (90th pct inside floor band), ridge peaks by prominence over flank medians (6.5-40 cm), pair peaks with 1.4-1.8 m spacing, dynamic-programming longest locally continuous chain of pairs (slope bound, gap <= 6 m), reject as UNKNOWN if a competing chain with >=85 % score lies >0.7 m laterally.
2. Observed pairs extended along the last tangent to 80 m (`curve_envelope_core.cpp:ExtendRailPairsForward`; arc/clamped-arc variants exist but are not active).
3. `AnalyzeCurveEnvelope`: points labelled CORE / MARGIN / OUTSIDE against a prism swept along the rail segments.
4. `ApplyBaselineV3`: connected components of CORE (radius 0.25 m, fixed); boundary rule rejects components by absolute sensor-frame coordinates; >=1000 points = strong obstacle; smaller ones go to the forest (8 features: count, extents, volume, density, centroid range, nearest range); separate "early candidate" cube/panel rule needs 3 frames.
5. Temporal confirmation 2 frames (forest) / 3 frames (early) in the adapters (`curve_envelope_node.cpp`, `curve_pipeline_stream_cli.cpp`); output JSON, status never CLEAR, `safety_decision_permitted=false`.

No detector-level technique here is worth porting. In particular do NOT port: the forest (features include centroid range and nearest range; several trees only fire for 55.0-56.7 m, volume 0.24-1.0 m^3, i.e. they memorise the single doubleT_obstacle event; `src/cpp/baseline_v3_assist_model.inc`, `models/baseline_v3_runtime_policy.json`), the `BaselineV3BoundaryWarning` rule (absolute sensor-frame centroid_x < -1.30 / centroid_z > 1.0), the `BaselineV3ExperimentalEarlyCandidate` cube/panel rule (hard-coded sizes 0.2-0.65 m and 1.1-2.6 m, >=80 points, >7 m), or the tangent extension to 80 m (no curve model: on curves the envelope leaves the track).

## Things done worse than ReSense / red flags
- Overfit by construction (authors say so): forest trained on 52 components of one event; the reported "first detection 55.58 m" is inside the range window that the trees learned (55.0-56.6 m). Hard negatives came from all six other real sources including the 20-min `new_data` ride (47 FP frames there are therefore in-sample, and episodes are not counted).
- Range is poor: only 0.3 m objects at ~10-14 m, 2x2 m at 8-68 m, obj09 (2 x 0.2 m on rails) first public detection at 3.3 m; fixed connectivity radius 0.25 m and 1000-point "strong" threshold are range-blind.
- No ego-motion, no accumulation, no per-range/size evaluation, no curve model (tangent only), fixed sensor axis `-Y` (their own doc), UNKNOWN is frequent.
- Evaluation labels are windows only (`config/evaluation_labels.json`), "6/6" counts any alarm in the window; obj05, obj08, obj10 unlocalized, obj09 ambiguous: excluded. Our per-frame labels (`labels/cloud_with_fake_obj.json`) are far more detailed.
- ROS path drops frames: 187/201 processed at p50 67 ms ("Message queue starved", `docs/reports/submission/HEADLESS_ROS2_CPP_PERFORMANCE.md`).
