# bq777xCube/lidar_project

## Verdict
Hybrid, classical geometry (Python/NumPy package `foreign_object_detector`, optional ctypes C kernel for beam selection). No learned model. Maturity: a documented hackathon submission with validation receipts, but the reported numbers are in-sample dev data (13/21 expected detections, 2/12 expected-ignore false alarms, 4/702 background inputs, 0/193 real controls, per `docs/RESULTS.md`). The headline 98-99 m detections are on the organizer's synthetic inserts and are driven by a dataset-specific beam-angle test (see red flags). Treat the near-field rail/gauge part as the reusable piece.

## Pipeline
1. `near/point_cloud.py`, `pointcloud_adapter.py`: read x/y/z FLOAT32 (any field order), drop zeros/NaN, cap at 180 m; canonical axes s=-Y, l=X, z=Z.
2. `near/rail_reference.py:estimate` + `near/rail_geometry.py:fit_frame`: ROI 5-20 m, |y|<=3 m, z in [-2.5, 0]; ridge histograms, 1500-trial RANSAC over ridge pairs (separation 1.35-1.85 m), plane fit (max RMS 2.5 cm).
3. `near/rail_frame.py:from_plane` (or `from_profile` fallback `default`): normalise frame from rail plane; reject if normalised head RMS > 5 cm.
4. `near/centerline.py:extend`: quadratic centreline along rails to 150 m with max gap 10 m, max extrapolation 2 m, height and separation checks.
5. `near/clearance.py`: Frenet gauge 2.1 m x 3.0 m (margins 0), hard mask of rail ellipse (0.10 m lateral, 0.04 m vertical) and everything below rail top -4 cm (points deleted, not soft).
6. `near/candidate.py:candidates`: occupancy components with range-banded cell sizes; >=3 points, >=2 cells, >=3 points above 4 cm.
7. `sparse_tracker.py`: 0.1 s nominal scan; sub-threshold clusters linked across frames by lateral/height gates and an apparent-approach window (-0.5..3 m/scan) with velocity innovation <=1 m; rule S2 = 3 hits in 5 frames, gap <=1.
8. `far.py` + `beam_selector.py`: synthetic-only far channel (>=60 m, <=180 m); accepts points whose elevation is >0.02 deg off the 128 calibrated beams, inside a fixed box in the nominal frame. Asset pinned by SHA-256.
9. `handoff.py`, `node.py`: merge normal/sparse/far results; publishes `/foreign_object/obstacle`, `/distance`, `/state` (OBSTACLE / CLEAR / TRACK_UNRELIABLE), `/horizon`, `/track_quality`.

## Things done worse than ReSense / red flags
- The synthetic far channel (`far.py`, `beam_selector.py`, `config/frozen_far.json`, SHA-256 pinned) flags points whose elevation is more than 0.02 deg off the 128 calibrated beams. This targets the organizer's insertion generator, not physical objects. The repo says so (`docs/ALGORITHM.md` §4, `RESULTS.md` "Область применимости"). The 98-99 m detections depend on it. Do not borrow. ReSense has no equivalent (grep `beam|elevation`: no detection use).
- `config/production.yaml` `pose_profiles.obstacle_recording` (height 1.503 m, lateral -3.45 deg) is a per-recording pose. It is not the default fallback, but it is recording-specific tuning, which the brief rules out.
- Dev numbers are in-sample and selected: reference points are hand highlights (`docs/assets/examples_provenance.json`, `reference_point_count`), and selected frame indices are hard-coded in provenance. 0/193 real controls is far too small to support a false-alarm claim.
- Dead code shipped: `v1_detector.py`, `v2_detector.py`, `v3_detector.py`, `_phase5b.py`, `v3/v4_fallback.yaml`. Only `production.yaml` is current.
- `validation/tools/parity_ru.py` imports `/workspace/experiments/rescue_query_first`, which is not in the repo, so that check cannot be reproduced from the repo.

## Eval/data tooling worth borrowing
- Results split into separate rows for expected-detect, expected-ignore, background and real controls, with unlabelled frames stated as excluded (`docs/RESULTS.md`). Copy this reporting style.
- `docs/assets/examples_provenance.json`: each figure lists source file, SHA-256, frame, selected index and what the highlight is. Good for reproducing a single example.
- `validation/check_repository.py`, `SHA256SUMS`, `source_integrity.json`: integrity checks on frozen assets (useful for pinning our own tuned configs).
- `tests/test_contract.py` and `scripts/watch_outputs.py` / `demo_monitor.py`: contract tests and a live output observer for replay.
