# Hramchik/MetroGuarder

Code root: `ros2_ws/src/rail_guard/rail_guard/lib/` (paths below are relative to it). README is a Docker how-to only; the real content is `docs/ALGORITHM.md`, `docs/EXPERIMENTS.md`, `docs/RESULTS.md` (Russian) and the pptx (text read as data only).

## Verdict
Classical geometry, no learning, same philosophy as ReSense ("describe the normal tunnel, flag what does not fit"). Mature engineering (51 synthetic unit tests, ROS 2 nodes, GPU path, auto-calibration) but **no labels and no FPR metric**: the authors say so themselves ("Что не получилось: измерить долю ложных срабатываний"). The headline claims (person detected to 120 m, "15 % -> 1 % false emergency", 0 false brakes on OSDaR23) are in-sample, small-n (6 injection trials per range, 30 OSDaR frames) and use a different output semantics (speed-dependent braking actions, not GO/STOP). Not directly comparable to our STOP-episodes/km and STOP-recall-by-range numbers.

## Pipeline
1. `frames.py`: auto forward/up axis from the cloud (compressed axis = up; one-sided axis = forward), decided once on first good frame. `sensor_model.py`: measure beam density k (pts/sr) from the stream, N = fill*k*A/r^2; all point-count thresholds and `detection_limit` derived from it (`derive.py`).
2. `preprocess.py`: range-banded voxel thinning (far field never thinned), adaptive density/range budget from measured frame time vs lidar period. `ground.py`: bed profile in 5 m cells tracked near-to-far with slope limit; cross-slope referenced to track axis.
3. `track.py:estimate_track`: axis by matching the cross-section to a rail template (two humps + dip) over arc hypotheses y=b*x+a*x^2, continuity limit (1.5 m @50 m vs previous frame), confidence = rail-visible range. Beyond it `estimate_tunnel_center` follows measured per-10 m-band tube centre / own wall.
4. `track.py:build_corridor`: 2.8 x 3.75 m gauge (NOT the task's 2.1 x 3.0) + 0.25 m lateral margin; length = trusted zone + margin sqrt(2*R_min*half) (or from measured axis jitter).
5. `tunnel.py` free-space model per frame (range band x 0.4 m height layer -> lateral boundary), `scene.py` enclosed/open classifier; candidates = corridor points above bed+8 cm, rails masked, radius-outlier filter.
6. `pipeline._accumulate`: far candidates (>= min_range) of last 5 frames shifted by ego travel (egomotion.py: occupancy-profile correlation, accel gate), range-scaled clustering (`cluster.py`).
7. `detect.py`: reject reasons (too_flat, long_low, ground_sheet, thin_along_track, sparse, sliver, overhead, wall, tunnel_surface, full_height, track_line), rejected clusters are DELETED. `tracking.py` 3-of-5 tracks, gate 0.04*r. `decision.py`: braking-distance vs range, kinematic gate (closing speed >= 0.35 v), service-brake only beyond rail-confirmed zone, >= 8 points for any brake.

## Things done worse than ReSense / red flags
- Min visible object: bed cut `ground_band` 8 cm + `min_size_z` 8 cm + `gauge.bottom` 0.10 m over rail head; their own docs say an object counts only if >= ~20 cm above ballast (~13 cm above rail head). A 30x30x10 cm object (task spec) is structurally invisible; no low-object stage (we have `lowobj.py`). `thin_along_track` (width < 0.30 m, length > 1 m) also hides a 0.3 m board lying along the track.
- STOP floor of 8 points regardless of range (`min_points_brake`), while we confirm far evidence with 3 voxels; tuned against false brakes, costs range. Their reported 120 m is "confirmed track" with service brake, and tested on 6 injected placements.
- The one real obstacle recording (`doubleT_obstacle`, train standing) yields 0 % braking and 89-96 % ATTENTION (EXPERIMENTS.md tables): decisions depend on speed (v=0 -> braking distance 0), so the single positive was never turned into an alarm; kinematic gate is switched off in their range test; target is injected on the axis estimated by the same pipeline (circular for axis errors). Presentation says "1 % false emergency" while the table shows 2-12 % service+emergency frames and attention 17-55 % on empty tunnels (comparable noise to our CAUTION 35-69 %).
- Gauge 2.8 x 3.75 m (+0.25) instead of the task's 2.1 x 3.0 m, so FP numbers are for a wider corridor and recall for a taller one; not transferable 1:1. Stale comments in config.py (gauge.bottom "5 cm") disagree with metro.yaml (0.10); README gives nothing.
- Axis in tight curves is poor without a route map (OSDaR R=250 m: 6.7 m error @70 m), switches "not solved" (admitted).

## Eval/data tooling worth borrowing
- Multi-start / dropped-frame sweep of every metric (idea 6); "Что не получилось" log format (each failed trick with the measured number) is a good habit and shows which intermediate metrics did not predict the final one (axis-stabilisation halved jitter, final metrics unchanged).
- `scripts/measure_sensor.py` (measure `fill` = points in GT cuboid / predicted by k*A/r^2 from labelled data; 0.56 median, 0.72 persons on OSDaR23): the same on our real person at 55-57 m would calibrate `expected_points` returns factor.
- Per-stage timing table and `scripts/check_gpu.py` style decision-parity check (compares decisions, not times) between backends; we have `--require-parity` already.
- OSDaR23 (open, labelled rails/objects, `poly3d` GT axis) used for axis-accuracy by range; could give a held-out axis test for `track.py` (mainline, not metro, so only geometry transfers).
