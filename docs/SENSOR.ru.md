# Датчик: Hesai Pandar128 (E3X)

> Перевод документа [SENSOR.md](SENSOR.md) (English). Английский оригинал — основной: при расхождении верен он.

> **Назначение:** что за LiDAR записал данные организаторов и на что он способен — по его
> руководству и по записям, и что из этого следует для детектора и оценки.
> **Аудитория:** команда, жюри · **Ответственный:** P1 · **Язык:** RU (перевод, оригинал EN)
> **Проверено:** 2026-09-29: цифры из руководства, ответы организаторов и текущие тайминги
> ноды · **Статус:** актуален

**Кратко.** Данные организаторов записаны лидаром Hesai Pandar128 (E3X): 128 каналов, 10 Гц; в
записях — окно 120° с шагом 0,1° по азимуту и 0,125° по вертикали около горизонта. По паспорту
200 м при отражательной способности 10 % дают только 32 канала у горизонта; ни в одной записи нет
точек дальше 210 м, поэтому 300 м для этого датчика недостижимы. Интенсивность — отражательная
способность в процентах (больше 100 — световозвращающие материалы). Лидар стоит на 1 075 мм выше
головки рельса по оси состава (ответ организаторов 24.09); автокалибровка измеряет 1,12 м.

Источник: руководство пользователя, выданное организаторами,
[`sensor/Pandar128E3X_v4p5_User_Manual_128-en-240710-1.pdf`](sensor/Pandar128E3X_v4p5_User_Manual_128-en-240710-1.pdf)
(Hesai 128-en-240710, июль 2024, sha256 `69c09eb2af5eb358e6d76559108238f15a1ee57b742560b8be8d7fce582e915a`;
номера разделов и приложений ниже — из руководства). Это раздаточный материал организаторов для
собственного использования команды: не распространять за пределами хакатона. Файл угловой
коррекции и модель STEP лежат на странице загрузок Hesai, https://www.hesaitech.com/downloads/#pandar128.
Значения «измерено» — то, что [`DATASET.ru.md`](DATASET.ru.md) нашёл в записях.

## 1. Идентификация

Записи сделаны **Pandar128**, а не датчиком серии AT, как предполагалось сначала:

| свойство | руководство (Pandar128) | измерено в бэгах |
|---|---|---|
| каналы | 128 | 128 колец |
| вертикальное поле зрения | 40° (−25° … +15°) | +14,40° … −25,12° |
| тонкая вертикальная полоса | 0,125° на каналах 26–90 (+2,01° … −6,10°) | шаг 0,125° на кольцах 26–90 (+2,0° … −6,2°) |
| грубые полосы | 0,5° на каналах 2–26 и 90–127, 1° по краям | 0,5° вне тонкой полосы |
| углы места по каналам | канал 1 = +14,436°, канал 128 = −25,016° (файл угловой коррекции) | кольцо 0 = +14,402°, кольцо 127 = −25,120°; все 128 в пределах 0,12° |
| горизонтальное разрешение | режим High Resolution при 10 Гц: 0,1° на каналах 26–89, 0,2° на остальных; Standard (по умолчанию) 0,2°; ближнее поле (< 2,85 м) 0,4° (§4.4) | сетка столбцов 0,1° (1200 столбцов для окна 120°) |
| горизонтальное поле зрения | 360°, настраиваемые окна по азимуту (до 5) | окно 120° (возвраты в пределах ±50°) или полный оборот |
| частота кадров | 10 Гц / 20 Гц | ~10 Гц |
| режимы возврата | одиночный (последний / самый сильный / первый) или двойной | двойной, 2 блока на выстрел |
| дальность | 0,3 … 200 м при отражательной способности 10 % | последние возвраты на 209,2–210,0 м в каждой записи |

`resense/sensor.py` хранит измеренные углы места колец (у каждого экземпляра датчика своя
калибровка).

## 2. Характеристики, важные для проекта

| параметр | значение | следствие |
|---|---|---|
| инструментальная дальность по каналам | **200 м только на каналах 26–89** (+2,0° … −6,0°); 100 м на остальных | дальше ~15 м коридор виден только каналам на 200 м: при высоте датчика 1,075 м у организаторов головка рельса находится под углом −0,6° на 100 м и −0,3° на 200 м |
| максимальная дальность при отражательной способности 10 % | **200 м на 32 каналах «усиленного дальнего поля» 34–65** (≈ +0,95° … −3,0°); 140 м на остальных каналах из 26–89 (для 200 м нужно 37 %) | тёмный объект обнаруживается на 200 м только в полосе ~4° вокруг горизонта — там, где находится препятствие 1–2 м на 100–200 м. **300 м — за пределами дальности** для обычных целей |
| точность измерения дальности | ±2 см (1–200 м); ±5 см ближе 1 м | сообщаемая дальность ограничена кластеризацией (ближайшая точка), а не датчиком |
| минимальная дальность | 0,3 м на 32 каналах ближнего поля, 2,7 м на остальных | `sensor.min_range` 2,5 м отбрасывает ближнее поле, в котором есть только собственный нос поезда |
| частота точек | 3 456 000 точек/с одиночный, 6 912 000 двойной (360°) | ~190 тыс. валидных точек на кадр 120°, ~347 тыс. при 360° |
| блоки двойного возврата | два блока на выстрел с одним азимутом (§3.1.2.3); в режимах Last и First одиночный возврат заполняет оба; в режиме Last and Strongest (по умолчанию) блок 2 содержит второй по силе | во всех семи записях 96–98 % точек идут одинаковыми парами (одно эхо в обоих блоках): 85–95 тыс. различных точек на кадр 120°. Детектор считает занятые воксели, поэтому копии не меняют ни одного решения |
| отражательная способность | 0–255, по умолчанию линейное отображение (значение = отражательная способность в %); > 100 для световозвращателей; два необязательных нелинейных отображения (Приложение C) | бэги соответствуют линейному отображению (медиана 6–7, рельсы и знаки 255): `intensity` — это отражательная способность в %. При нелинейном отображении `cluster.retro_intensity` пришлось бы вывести заново |
| часы | GNSS или PTP, ≤ 1 мкс; без источника часы стартуют с виртуального 2000-01-01 | в бэгах нет источника часов: используется время приёма в бэге; поточечной компенсации движения (deskew) нет |
| встроенный IMU | хвост каждого пакета содержит трёхосевое ускорение и угловую скорость (§3.1.2.5) | этого достаточно для компенсации вибрации / тангажа, но сообщения `PointCloud2` их не несут; решение работает без IMU и без входа скорости (§4) |
| заводские настройки (§4) | 10 Гц, Last and Strongest, разрешение Standard (0,2°), линейная отражательная способность, азимутальное поле зрения 0–360° | записывавший датчик был перенастроен (столбцы 0,1°, окно 120°); контрольные данные используют те же настройки (§4), так что бюджет точек из [`DATASET.ru.md`](DATASET.ru.md), «Бюджет точек по дальности», остаётся в силе |
| развёртка и движение | одно окно 120° разворачивается за 33 мс; при 80 км/ч это 0,7 м пути внутри кадра, 2,2 м между кадрами | для накопления по нескольким кадрам нужно собственное движение (ego-motion) в каждом кадре; поточечная компенсация движения (deskew) имела бы значение выше ~40 км/ч |
| система координат | Z = ось вращения, Y = азимут 0°, по часовой стрелке (вид сверху) | в бэгах вперёд = −Y, влево = +X, вверх = +Z; это задают `sensor.forward/left/up` в `configs/default.yaml`, и больше ничто не зависит от модели |
| механика | 1,63 кг, Ø116 × 124 мм, IP6K7 / IP6K9K, −40 … 85 °C, 23–27 Вт, ISO 26262 ASIL B | датчик автомобильного класса |

## 3. Следствия для алгоритма и оценки

1. **Дальность.** ТЗ §8.2 оценивает 300 м как отличный результат; цель с отражательной
   способностью 10 % инструментально измеряется до 200 м, и то только на 32 каналах у горизонта, а
   ни в одной записи нет возвратов дальше ~210 м. Интервалы дальности при оценке
   ([`EVALUATION.ru.md`](EVALUATION.ru.md) §2) сохраняют 200–300 м только для полноты.
2. **Коридор находится в лучших каналах.** Дальше ~15 м полотно и всё, что на нём, видят каналы с
   шагом 0,125° × 0,1°, дальше ~30 м — каналы с усиленным дальним полем; априорная оценка
   ожидаемого числа точек в `resense/sensor.py` использует этот мелкий шаг. Ограничение 100 м у
   грубых каналов сказывается только на своде и ближнем полотне.
3. **Отражательная способность откалибрована.** Порог выше 100 выделяет световозвращающие
   материалы (знаки, отполированные головки рельсов): правило световозвращателей
   ([`ALGORITHM.ru.md`](ALGORITHM.ru.md) §3.3, пункт 6), по умолчанию выключено
   (`cluster.retro_intensity: 0`: на шести бэгах оно ни разу не сработало).
4. **Собственное движение (ego-motion).** С PTP каждая точка несла бы метку времени в мкс, и
   накопление могло бы компенсировать движение внутри кадра (deskew); организаторы сказали, что в
   рамках этого хакатона этого не будет.
5. **Другой экземпляр датчика или другое крепление.** Детектор никогда не использует индекс
   кольца; таблицу углов места используют только `resense inject` и априорная оценка ожидаемого
   числа точек. Другой Pandar128 или другое крепление не требует изменений кода (крепление
   калибруется по данным); другая модель ухудшила бы только инжектор и оценку видимости.
6. **Запас по потоку данных.** В полном обороте втрое больше слотов, чем в окне 120°.
   Декодирование в ноде занимает 16,6 мс (медиана) при 360° и 4,8 мс при 120° (с 29.09); с
   нативными ядрами декодирование + обнаружение укладываются в период 100 мс на 4 ядрах (тайминги:
   [`SCORECARD.ru.md`](SCORECARD.ru.md), [`EXPERIMENTS.ru.md`](EXPERIMENTS.ru.md)); запасной вариант на
   numpy при 360° не успевает. Обрезка по дальности и азимуту выполняется после декодирования,
   поэтому более широкое окно стоит только времени декодирования.

## 4. Вопросы организаторам (получены ответы)

* **Режим возврата, разрешение и окно** (24.09, [`organizers/answers.md`](organizers/answers.md)
  §3). Сейчас датчик работает в режиме Last and Strongest; выданные записи, особенно
  `doubleT_obstacle`, старые и могли быть сделаны в другом режиме; **контрольные данные используют
  те же настройки**. Обе пары (топик, frame id) могут встретиться, с одного LiDAR (ответы от
  23.09).
* **Время PTP / GNSS.** На поезде оно будет, но не в рамках этого хакатона: часами остаются время
  приёма в бэге и разности `header.stamp` с эпохой 2000 года.
* **Крепление.** Между поездами не фиксировано («рассчитывайте на переменное положение, задавайте
  его в параметрах запуска», 22.09); тестовые бэги используют крепления выданных записей, с LiDAR
  **на 1 075 мм выше головки рельса, по оси состава**, числового значения ориентации нет
  ([`organizers/mount_and_switch_qa.md`](organizers/mount_and_switch_qa.md)). Калибровка измеряет
  1,12 м (боковое смещение −0,02 м) на `roundT_doubleT` и 1,51 м при крене +3,0° на более старой
  установке `doubleT_obstacle`, поэтому она остаётся включённой как страховка, вместе с
  аргументами запуска для крепления ([`ALGORITHM.ru.md`](ALGORITHM.ru.md) §2b).
* **Скорость поезда.** В записях нет одометрии, а на некоторых поездах её нет вовсе (Q&A 22.09):
  решение работает без скорости, одометрии и IMU; входы скорости ноды остаются необязательными, а
  накопление по нескольким кадрам выключено, пока скорость не задана. Оценка скорости только по
  LiDAR точна (медианная ошибка 0,06–0,08 м/с), но не улучшает проверку организаторов, поэтому
  остаётся включаемой по желанию ([журнал экспериментов](archive/EXPERIMENTS_log_2026-09.md) §9).
